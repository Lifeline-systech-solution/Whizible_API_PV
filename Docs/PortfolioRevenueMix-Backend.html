1. What was studied before coding

  1. Page PM_AnalyticsCXO_Dashboard.aspx loads KPI cards through GetAnalyticsDBKPICards using the same date range and chip IDs (Portfolio, Customer, Project Manager, Region, Billing Type, Health).
  2. Revenue card Flag maps to stored procedure usp_Whizible2_Sel_AnalyticsDBKPI_Revenue.
  3. Revenue drill-through uses POST /api/PM_AnalyticsCXO_Dashboard/GetAnalyticsDBRevenueDrillDown → usp_Whizible2_Sel_AnalyticsDB_RevenueDrillDown.
  4. Existing C# pattern: Controller → PM_AnalyticsCXO_Dashboard service → SQL parameters → ResponseHelper.BuildResponse. Drill-down rows are string dictionaries because each level has different columns.
  5. No ASPX, JavaScript, chart, or CSS files were changed.

2. How existing Revenue KPI actually calculates Revenue

Source of truth is usp_Whizible2_Sel_AnalyticsDBKPI_Revenue, not a guessed column name.

  • Fact table: Tbl_PM_ProjectProfitability (period row keyed by PP.ToDate).
  • Project: Tbl_PM_Project on ProjectID.
  • Portfolio: P.ProjectGroupID left-joined to Tbl_PM_ProjectGroup (ProjectGroupName).
  • Health: INNER JOIN dbo.fn_Whizible2_Get_ProjectOverallHealth(@HealthIDs).
  • Currency: company BaseCurrencyID; if project currency differs, tbl_PM_Currency_Detail.ConversionRate for the profitability ToDate.
RawRevenue =
  ContractType = 1 (fixed price / milestone):
      PeriodicMilestoneBilledAmount + PeriodicBillableOtherCostTotal
  Else (T&M / accrued):
      PeriodicAccruedResourceBillingTotal + PeriodicBillableOtherCostTotal

ConvertedRevenue = RawRevenue * ExchangeRate
Current KPI value = SUM(ConvertedRevenue) where PP.ToDate is in CurrentFrom–CurrentTo

The KPI SP also builds previous-period totals and a “growth led by {portfolio}” note. Those are not needed on the mix chart. Mix uses only the current-period converted revenue, which is the KPI card’s CurrentValue.

4. Existing Revenue drill-down (unchanged)

  • Endpoint: GetAnalyticsDBRevenueDrillDown
  • SP: usp_Whizible2_Sel_AnalyticsDB_RevenueDrillDown
  • Level 1 = all matching portfolios (INNER JOIN Project Group → Project, so empty groups and unmapped projects are omitted).
  • Level 2+ uses @PortfolioID plus the same chip filters. Level 2 already restricts to one group.
  • This endpoint was not modified. Mix chart must not call it if a slice click should hide other portfolios at Level 1.

5. What was developed — Portfolio Revenue Mix

5.1 Stored procedure

Scripts\usp_Whizible2_Sel_AnalyticsDB_PortfolioRevenueMix.sql
Name: usp_Whizible2_Sel_AnalyticsDB_PortfolioRevenueMix

  • Copies the KPI BaseData revenue formula, health join, currency join, and the same Customer / Portfolio / Billing / Region filters.
  • Restricts profitability rows to the current date range only.
  • Groups by Project Group instead of returning one total.
  • Result columns: PortfolioID, PortfolioName, Revenue (varchar decimal, same AutoMapper-safe style as KPI), RevenueFormatted, BaseCurrencyCode.

5.2 API

POST /api/PM_AnalyticsCXO_Dashboard/GetAnalyticsDBPortfolioRevenueMix

Request model AnalyticsDBPortfolioRevenueMixRequest — same dates and chip ID lists as GetAnalyticsDBKPICards.

Response data is a list of:

{
  "portfolioID": 1,
  "portfolioName": "P1",
  "revenue": 1500000,
  "revenueFormatted": "S$15.00 L",
  "baseCurrencyCode": "S$"
}

6. Empty portfolios vs unmapped projects

Case A — Portfolio exists, no projects (or none that pass other filters)
If that group is in @PortfolioIDs, the mix SP seeds from Tbl_PM_ProjectGroup and left-joins revenue. The group is still returned with Revenue = 0.
Case B — Project exists, ProjectGroupID is NULL
KPI includes those projects only when @PortfolioIDs is blank (the IN-list cannot match NULL). Mix does the same: they appear as PortfolioID = 0, PortfolioName = "Unmapped". If specific portfolios are selected, unmapped revenue is excluded so SUM(mix) still equals the Revenue KPI.

When no portfolio chip is selected, mix returns only groups (plus Unmapped) that have current-period KPI revenue. Empty unused groups are not listed, to avoid filling the donut with zeros.

7. Revenue consistency rule

For one filter context:

SUM(mix.Revenue) = GetAnalyticsDBKPICards Flag=Revenue → CurrentValue
  • Same formula, same joins, same current dates, same chip filters.
  • @ProjectManagerIDs ignored on both, matching the KPI SP as written.
  • Unmapped included in the sum only when Portfolio chip is empty.
  • Selected empty groups add 0 and do not change the sum.

8. What was developed — Portfolio Revenue Mix drill-down

8.1 Stored procedure

Scripts\usp_Whizible2_Sel_AnalyticsDB_PortfolioRevenueMixDrillDown.sql
Name: usp_Whizible2_Sel_AnalyticsDB_PortfolioRevenueMixDrillDown

  • Clicked @PortfolioID always wins. It overwrites @PortfolioIDs so P2/P3 cannot leak into a P1 click.
  • Level 1 is implemented in this SP: one group only, LEFT JOIN projects so a group with no projects still returns a zero row. Existing Level 1 INNER JOIN would drop that group.
  • Levels 2–6 for a mapped group EXEC the existing usp_Whizible2_Sel_AnalyticsDB_RevenueDrillDown (same invoices → lines → timesheet/milestone/deliverable logic).
  • @PortfolioID = 0 means Unmapped: every level filters P.ProjectGroupID IS NULL. The old SP’s ProjectGroupID = 0 would not match NULL.

8.2 API

POST /api/PM_AnalyticsCXO_Dashboard/GetAnalyticsDBPortfolioRevenueMixDrillDown

Request: AnalyticsDBPortfolioRevenueMixDrillDownRequest

  • Same dashboard dates and chips as the Revenue drill-down.
  • PortfolioID is required. Use 0 for Unmapped.
  • Level 2 does not require a second id (the slice already is the group). Level 3 still needs ProjectID. Level 4+ still needs InvoiceID.
  • InvoiceItemIDs is passed through for Level 5 (existing public Revenue drill request did not send this).

Response reuses AnalyticsDBRevenueDrillDownModel: Level, LevelLabel, Rows (same column names as the existing drill table so the future UI can bind the same way).

Clicked P1 + Customer C1 + Region R1 + Billing T&M + Current Quarter
        → Level 1: P1 only
        → Level 2: projects under P1 with those filters
        → Level 3–6: existing revenue hierarchy, still inside P1

10. Suggested frontend contract (not implemented here)

  1. Donut: call GetAnalyticsDBPortfolioRevenueMix with the same body as buildKpiCardsRequest.
  2. Slice click: call GetAnalyticsDBPortfolioRevenueMixDrillDown with that slice’s PortfolioID, keep other chips, start at Level 1 or Level 2.
  3. Do not reuse GetAnalyticsDBRevenueDrillDown for the mix chart if Level 1 must be a single slice.

11. Point-wise understanding (summary)

  1. Portfolio in this product is Project Group (Tbl_PM_ProjectGroup / Tbl_PM_Project.ProjectGroupID).
  2. Revenue is profitability-period based, contract-type branched, then converted to base currency.
  3. The mix API is the KPI calculation grouped by that Project Group.
  4. Selected groups with no work stay in the mix as zero.
  5. Unmapped work is a separate bucket named Unmapped (id 0), only when the portfolio chip is not narrowing the set.
  6. Mix drill-down is a new API/SP so a slice cannot return sibling portfolios.
  7. Deeper drill levels reuse the existing Revenue drill-down SP for mapped groups.
  8. Existing Revenue card, existing Revenue drill API, and all frontend files were left as they are.
